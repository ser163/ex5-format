            .ex5 File Format Specification, Version 1.1

Status of This Memo

   This document specifies an informational protocol for the EX5 community.
   It does not specify an Internet standard of any kind. Distribution of
   this memo is unlimited.

Abstract

   The .ex5 file format is a novel electronic book container designed to
   encapsulate book content, multimedia resources, and user interaction
   data such as reading progress, notes, and ratings. This specification
   defines Version 1.1 of the .ex5 format, leveraging ZIP archives, JSON,
   SQLite, and XML to enable secure storage, rich functionality, and
   remote synchronization. Version 1.1 adds multi-user shared
   annotations: in unencrypted files, notes, excerpts, inspirations,
   highlights, reviews, and ratings are readable by everyone holding the
   file, while only the original author may edit them. This document
   provides a detailed protocol for developers to implement
   .ex5-compliant applications.

1. Introduction

1.1 Purpose

   The .ex5 file format is designed to provide a robust, extensible, and
   user-centric solution for electronic books. It aims to:
   - Store multimedia book content (text, images, audio, video).
   - Track user interactions (progress, notes, ratings).
   - Support secure encryption and compression.
   - Enable synchronization across devices via a remote server.
   - Support multi-user sharing of notes, excerpts, inspirations,
     highlights, reviews, and ratings (unencrypted files only).

1.2 Scope

   This document defines Version 1.1 of the .ex5 protocol, covering file
   structure, data schemas, encryption, and synchronization mechanisms.
   Future versions may extend this specification.

1.3 Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this
   document are to be interpreted as described in RFC 2119.

2. Protocol Overview

2.1 File Structure

   A .ex5 file is a ZIP archive containing:
   - book_data/: Static book metadata and structure.
   - resources/: Multimedia resource files.
   - read_data.db: SQLite database for user data.
   - meta.xml: Protocol metadata.

2.2 Versioning

   This specification defines Version 1.1. The version is indicated in
   the meta.xml file. Future revisions will increment the version number
   (e.g., 1.2, 2.0) and document changes explicitly.

   Changes from Version 1.0 to 1.1:
   - Added a multi-user shared-annotation and permission model
     (Section 5.4): in unencrypted files, every user's notes, excerpts,
     inspirations, highlights, reviews, and ratings are readable by all,
     and editable only by their original author.
   - Added a uuid column to the notes, inspiration, reviews, and ratings
     tables for deduplication during cross-user and cross-device merges.
   - Clarified resource ID ranges, reserved encrypt_scope values,
     encryption algorithm details, and the plaintext requirement for
     meta.xml.

3. File Format Specification

3.1 Container Format

   - Format: ZIP archive (DEFLATED compression).
   - Extension: .ex5.
   - Requirement: Implementations MUST support ZIP extraction and creation.

3.2 book_data Directory

   The book_data/ directory contains three JSON files:

3.2.1 info.json

   Defines book metadata:
   {
     "title": STRING (max 1000 chars, UTF-8),
     "authors": ARRAY[STRING] (max 50 elements),
     "translators": ARRAY[STRING] (max 50 elements, optional),
     "pub_date": INTEGER (Unix timestamp),
     "version": STRING (max 50 chars),
     "publisher": STRING (max 200 chars, optional),
     "cover_id": INTEGER (0-100),
     "chapter_count": INTEGER (0-100000),
     "word_count": INTEGER (0-10^9)
   }

3.2.2 chapters.json

   Defines chapter structure:
   [
     {
       "index": INTEGER (1-100000),
       "title": STRING (max 500 chars, optional),
       "resource_ids": ARRAY[INTEGER] (max 1000 elements, refs resources.json)
     }
   ]

3.2.3 resources.json

   Defines resource metadata:
   [
     {
       "resource_id": INTEGER (0-1001000),
       "content": STRING (filename in resources/),
       "type": ENUM ("txt", "image", "html", "video", "sound", "binary"),
       "resType": STRING (max 20 chars, optional, e.g., "png" for image)
     }
   ]
   - Constraints:
     - 0-100: Cover resources (referenced by the cover_id field in
       info.json).
     - 101-900: Reserved for future versions; implementations MUST NOT
       assign content resources in this range.
     - 901-1001000: Content resources.

3.3 resources Directory

   Contains physical resource files (e.g., cover.png, chapter1.txt).
   Filenames MUST match the "content" field in resources.json.

3.4 read_data.db SQLite Database

   A SQLite database with the following tables. read_data.db natively
   supports multiple users via the users table: annotations,
   inspirations, reviews, and other data from several users of the same
   book coexist in one database; sharing semantics are defined in
   Section 5.4.

3.4.1 users Table
   CREATE TABLE users (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       identifier TEXT NOT NULL UNIQUE,
       name TEXT,
       gender TEXT,
       birth_date INTEGER,
       lock INTEGER DEFAULT 0 CHECK (lock IN (0, 1)),
       cipher BLOB
   );

3.4.2 history Table
   CREATE TABLE history (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       read_count INTEGER DEFAULT 1,
       user_id INTEGER NOT NULL,
       start_time INTEGER NOT NULL,
       end_time INTEGER,
       duration INTEGER,
       status INTEGER DEFAULT 0 CHECK (status IN (0, 1, 2)),
       progress TEXT,
       FOREIGN KEY (user_id) REFERENCES users(id)
   );
   - Note: progress stores a textual summary of the latest reading
     position. A JSON-encoded object is RECOMMENDED (e.g.,
     {"chapter": 3, "offset": 128}), distinguishing it from the numeric
     progress values in the records table.

3.4.3 records Table
   CREATE TABLE records (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       history_id INTEGER NOT NULL,
       user_id INTEGER NOT NULL,
       start_time INTEGER NOT NULL,
       end_time INTEGER NOT NULL,
       progress REAL NOT NULL CHECK (progress >= 0 AND progress <= 100),
       duration INTEGER NOT NULL,
       start_chapter INTEGER,
       end_chapter INTEGER,
       record_time INTEGER NOT NULL,
       FOREIGN KEY (history_id) REFERENCES history(id),
       FOREIGN KEY (user_id) REFERENCES users(id)
   );

3.4.4 notes Table
   CREATE TABLE notes (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       uuid TEXT UNIQUE,
       content TEXT,
       type TEXT NOT NULL CHECK (type IN ('txt', 'image', 'html', 'video', 'sound', 'binary')),
       create_time INTEGER NOT NULL,
       update_time INTEGER,
       user_id INTEGER NOT NULL,
       chapter_id INTEGER,
       history_id INTEGER,
       records_id INTEGER,
       range_start INTEGER,
       range_end INTEGER,
       original TEXT,
       FOREIGN KEY (user_id) REFERENCES users(id),
       FOREIGN KEY (history_id) REFERENCES history(id),
       FOREIGN KEY (records_id) REFERENCES records(id)
   );
   - Notes:
     - content: For "txt", text string; otherwise, JSON array of resource_ids.
     - range_start, range_end: Character offsets for highlights (optional).
     - original: Highlighted text (optional).
     - chapter_id: Corresponds to the chapter index in chapters.json
       (chapters are defined in JSON, not in the database, hence no
       foreign key).
     - uuid: Globally unique record identifier (UUID v4 RECOMMENDED),
       generated at creation; used for deduplication and conflict
       resolution in cross-user and cross-device merges (see
       Section 5.4).
     - Feature mapping: a note is a record with content; an excerpt is a
       record with original and range_start/range_end; a highlight is a
       record with only range_start/range_end and no content.

3.4.5 inspiration Table

   CREATE TABLE inspiration (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       uuid TEXT UNIQUE,
       type TEXT NOT NULL CHECK (type IN ('txt', 'image', 'html', 'video', 'sound', 'binary')),
       content TEXT,
       create_time INTEGER NOT NULL,
       update_time INTEGER,
       user_id INTEGER NOT NULL,
       chapter_id INTEGER,
       history_id INTEGER,
       records_id INTEGER,
       FOREIGN KEY (user_id) REFERENCES users(id),
       FOREIGN KEY (history_id) REFERENCES history(id),
       FOREIGN KEY (records_id) REFERENCES records(id)
   );
   - Note: The uuid field has the same semantics as in the notes table.
     Inspirations correspond to rows of the inspiration table.

3.4.6 reviews Table
   CREATE TABLE reviews (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       uuid TEXT UNIQUE,
       content TEXT NOT NULL,
       user_id INTEGER NOT NULL,
       create_time INTEGER NOT NULL,
       update_time INTEGER,
       FOREIGN KEY (user_id) REFERENCES users(id)
   );

3.4.7 ratings Table
   CREATE TABLE ratings (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       uuid TEXT UNIQUE,
       user_id INTEGER NOT NULL,
       rating INTEGER NOT NULL CHECK (rating >= 1 AND rating <= 5),
       create_time INTEGER NOT NULL,
       update_time INTEGER,
       FOREIGN KEY (user_id) REFERENCES users(id)
   );

3.5 meta.xml Metadata

   <?xml version="1.0" encoding="UTF-8"?>
   <meta>
     <version>1.1</version>
     <encryption>AES-256</encryption>
     <encrypt_scope>7</encrypt_scope>
   </meta>
   - version: Protocol version (MUST be "1.1" for this spec).
   - encryption: Encryption algorithm (RECOMMENDED: AES-256).
   - encrypt_scope: Integer (0-7; 7 = full encryption of everything
     except meta.xml; values 1-3 are reserved and undefined). Shared
     annotations require this value to be 0 (see Section 5.4).
   - meta.xml MUST remain unencrypted under every encrypt_scope value
     (see Section 4.1).

4. Encryption and Compression

4.1 Encryption Mechanism

   - Targets: resources/, read_data.db, or the entire file.
   - Algorithm: AES-256 (default). GCM mode is RECOMMENDED for
     ciphertext integrity; if CBC mode is used, an HMAC MUST be
     appended for integrity protection.
   - Scope (encrypt_scope):
     0: None
     1-3: Reserved and undefined; implementations encountering these
          values SHOULD refuse to parse and report an error
     4: resources/ only
     5: resources/ and book_data/
     6: resources/ and read_data.db
     7: Everything except meta.xml (meta.xml MUST always remain
        unencrypted; otherwise implementations cannot read the
        encryption parameters)
   - Key: Derived via PBKDF2 (HMAC-SHA-256, at least 100,000 iterations,
     random salt) from the user password (RECOMMENDED). The salt and a
     fresh IV per encryption MUST be stored alongside the ciphertext.
   - Order: Encryption MUST be applied to the target content BEFORE ZIP
     compression (encrypted data cannot be compressed effectively).

4.2 Compression Mechanism

   - Target: Entire .ex5 file.
   - Algorithm: ZIP with DEFLATE.
   - Requirement: Implementations MUST use ZIP compression.

5. Remote Synchronization Protocol

5.1 Synchronization Overview

   - Goal: Synchronize read_data.db across devices.
   - Method: Incremental updates based on timestamps.

5.2 RESTful API Definition

5.2.1 GET /sync/read_data
   - Parameters:
     - user_id: STRING (corresponds to the identifier field of the
       users table)
     - last_sync_time: INTEGER (Unix timestamp)
   - Response:
     {
       "status": "success",
       "data": {
         "users": ARRAY,
         "history": ARRAY,
         "records": ARRAY,
         "notes": ARRAY,
         "inspiration": ARRAY,
         "reviews": ARRAY,
         "ratings": ARRAY
       },
       "timestamp": INTEGER
     }
   - Note: For unencrypted files, the response SHOULD include the notes,
     inspiration, reviews, and ratings of ALL users of the book (shared
     reading, see Section 5.4); private reading data such as history and
     records MUST still be limited to the requesting user.

5.2.2 POST /sync/read_data
   - Request Body:
     {
       "user_id": STRING (corresponds to the identifier field of the
                  users table),
       "last_sync_time": INTEGER,
       "data": OBJECT (matching read_data.db tables)
     }
   - Response:
     {
       "status": "success",
       "timestamp": INTEGER
     }
   - Note: The server MUST apply changes only to records belonging to
     the requesting user (user_id); modifications or deletions targeting
     other users' records MUST be rejected (see Section 5.4).

5.3 Conflict Resolution

   - Strategy: Last-write-wins based on update_time or create_time;
     when timestamps are equal, the record with the larger id wins.
   - Optional: Manual conflict resolution by user.

5.4 Shared Annotations and Permissions

   Notes, excerpts, inspirations, highlights, reviews, and ratings are
   content about this book and are naturally shared along with the .ex5
   file. The rules are:

   - Precondition: Sharing takes effect only when encrypt_scope in
     meta.xml is 0 (unencrypted). For encrypted files, implementations
     MUST display only the current user's own data.
   - Shared reading: In an unencrypted file, implementations MUST allow
     any user to read the notes, inspiration, reviews, and ratings of
     ALL users in read_data.db; when displaying them, the author's name
     SHOULD be resolved by joining user_id to the users table.
   - Edit permission: Only the original author may modify or delete
     their own records. Implementations MUST determine authorship by
     matching the currently logged-in user's identifier against the
     record's owning users.identifier, and MUST reject any edit
     targeting another user's records; the server enforces the same
     check in Section 5.2.2.
   - Multi-user merge: When copies of the same book circulate among
     users or are merged by a server, users are matched by
     users.identifier and records by uuid; records with the same uuid
     but different content are resolved by last-write-wins on
     update_time. Local autoincrement ids are valid only within one
     database and SHOULD be reassigned during merges.
   - Private data: history and records are personal reading-behavior
     data; they are not part of shared display and are used only for
     the owner's multi-device synchronization.

6. Implementation Guidelines

6.1 Parsing and Writing .ex5 Files

   Implementations MUST:
   - Extract ZIP archive.
   - Parse JSON and XML files.
   - Access SQLite database with schema validation.
   - Handle encryption as specified.
   - Display notes, inspirations, reviews, and ratings of other users
     (identifier different from the current user) as read-only, with no
     editing entry point.

6.2 Example Implementations

   Python Example (Reading Notes):
   import zipfile, sqlite3
   with zipfile.ZipFile('book.ex5', 'r') as z:
       z.extract('read_data.db', 'temp/')
   conn = sqlite3.connect('temp/read_data.db')
   cursor = conn.cursor()
   cursor.execute("SELECT * FROM notes")
   notes = cursor.fetchall()
   conn.close()

7. Security Considerations

   - Encryption: Use strong keys and secure key management; keys or
     user passwords MUST NOT be stored in plaintext inside the .ex5
     file.
   - Synchronization: Use HTTPS for API calls.
   - Data Validation: Validate all inputs to prevent injection attacks.
   - Decompression Safety: Implementations SHOULD limit the total
     decompressed size and file count to mitigate ZIP bomb attacks.
   - Sharing Privacy: In an unencrypted file, all notes, inspirations,
     reviews, and ratings are visible to anyone holding the file;
     implementations SHOULD clearly inform users of this when they
     create such content. Users needing privacy SHOULD enable
     encryption.
   - Identity Verification: The server MUST authenticate the requester
     via tokens to prevent forging an identifier to impersonate another
     user when publishing or modifying content.
